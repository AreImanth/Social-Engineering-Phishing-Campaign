# Social Engineering-Phishing-Campaign and Awareness Simulator

A training tool for creating and teaching phishing awareness through realistic (but non-harmful) simulated login pages, campaign tracking, and a post-simulation red-flags briefing.

## Design Principle

Students still get the full teaching experience: they see a convincing fake login page, "submit" credentials, and get redirected to an awareness page explaining the red flags. What's different is that the harvesting mechanism is removed **at the architecture level**, not just disabled by a flag.

- Mock pages mimic the *look* of a login flow using fictional brand names (SocialConnect, MailSecure, StreamFlix) — not literal clones of real companies' pages or trademarks.
- The "Log in" button is handled entirely client-side: it clears the typed value and sends only a content-free event (`campaign_id` + `target` + event name) — **never** the username/password — before redirecting to the awareness page.
- No Flask route in the project ever reads `request.form` for credential fields. This is verifiable by inspection (`grep server/app.py`).
- Anything that looks like "captured data" in the dashboard/PDF report is synthetic sample data generated by `data/seed_data.py` — fabricated target emails and fabricated sample passwords, hashed only to demonstrate the hashing module.
- `core/hashing.py`, `anti_phishing/detector.py`, `gui/dashboard.py`, and `gui/report_generator.py` are fully real, functional modules — only the live credential-capture pathway was removed.

## Why the Original Spec Wasn't Built As-Is

The original spec called for a phishing simulation kit with mock login clones of real companies (Facebook, Google, Netflix) that captured, hashed, and stored submitted credentials in a local database, tracked opens/clicks via a tracking pixel, and redirected to an awareness page afterward.

That version was not built. A functioning credential harvester is the same artifact regardless of stated intent (classroom demo vs. real attack) — once built, it's fully capable of collecting real people's real passwords. The redirect-to-awareness step doesn't change that; it happens *after* the harmful part (capturing and storing a real credential) has already occurred.

## Module Reference

### Entry Point

**`main.py`**
- Starts the Flask demo server in a background daemon thread.
- Opens the default browser to the server's index page.
- Hands control to `gui/dashboard.py`'s interactive menu loop.
- Entry point for the whole demo: `python main.py`.

**`data/seed_data.py`**
- Populates `core/campaign.py` and `core/database.py` with entirely fabricated data: fictional target emails at a non-existent `classroom-demo.local` domain, and made-up sample password strings.
- Hashes those sample strings via `core/hashing.py` purely to illustrate "why you'd hash instead of storing plaintext" — never touches real user input from the live pages.
- Must be run once before a demo (`python data/seed_data.py`) so the dashboard/report have something to display.

### core/

| File | Description |
|---|---|
| `__init__.py` | Package marker; documents that this package only ever operates on synthetic data, never on live form submissions. |
| `campaign.py` | Functions: `create_campaign()`, `record_event()`, `get_campaign()`, `get_all_campaigns()`, `campaign_summary()`. File-backed (JSON) state machine tracking each target's boolean lifecycle flags: sent / opened / clicked / submitted. `record_event()` only accepts four fixed event names — there's no parameter for credential content, so no code path could smuggle a password through it. |
| `database.py` | Functions: `read_all()`, `write_record()`, `clear_all()`. Thread-safe (via a re-entrant lock) JSON-backed store. Holds only whatever `data/seed_data.py` explicitly writes into it — the Flask app never calls `write_record()` from a request handler. |
| `hashing.py` | Functions: `hash_with_bcrypt()`, `verify_bcrypt()`, `hash_with_sha256()`. Real, working bcrypt (with a salted-SHA256 fallback if the bcrypt C-extension isn't installed) and SHA-256 hashing, used on the seed data so students can see plaintext vs. hash side by side in the dashboard/report. |
| `tracker.py` | Functions: `simulate_send()`, `register_open()`, `register_click()`, `register_awareness_redirect()`. Emulates email dispatch (no real email is ever sent) and wraps `campaign.record_event()` for each lifecycle stage. Also holds the raw bytes of a 1x1 transparent PNG used as the tracking pixel. |

### server/

**`app.py`** — Flask routes:

| Method | Route | Description |
|---|---|---|
| `GET` | `/` | Lists the demo pages |
| `GET` | `/phish/<page>/<campaign_id>/<target>` | Serves a mock login page, records a "clicked" event |
| `GET` | `/phish/track/<campaign_id>/<target>.png` | Serves the tracking pixel, records an "opened" event |
| `POST` | `/phish/event` | Records **only** a boolean lifecycle event (`campaign_id` + `target` + event name from a fixed allow-list) — any other fields sent by the client are ignored, not stored, not logged |
| `GET` | `/phish/awareness` | Renders the training page |

No route reads `request.form` for a username/password field anywhere in this file — the whole "login" interaction happens client-side in the template's `<script>` block.

**Templates** (`socialconnect.html`, `mailsecure.html`, `streamflix.html`)
- Stylized, original mockups using fictional brand names (not clones of real companies' markup or trademarks).
- Each includes an on-page banner stating it's a training simulation, an embedded tracking-pixel `<img>`, and a form whose submit handler:
  1. Clears the typed username/password fields immediately
  2. Sends only `{campaign_id, target, event: "submitted"}` to `/phish/event`
  3. Redirects to `/phish/awareness`

**`awareness.html`**
- The post-simulation training page. Explains the specific red flags (mismatched URL, urgency language, off-brand styling, unsolicited login prompt) and explicitly confirms that nothing typed on the previous page was transmitted or stored.

### gui/

| File | Description |
|---|---|
| `__init__.py` | Package marker for the operator console. |
| `dashboard.py` | Interactive CLI menu with four actions: (1) view campaign metrics, (2) view the synthetic sample database, (3) run `anti_phishing/detector.py` against sample URLs, (4) generate the PDF report. Pulls data only from `core/campaign.py` and `core/database.py`. |
| `report_generator.py` | `generate_report()` — uses ReportLab to build `data/campaign_report.pdf`: a campaign-metrics table, a synthetic-sample-dataset table, and a "key takeaways" section for students. |

### anti_phishing/

| File | Description |
|---|---|
| `__init__.py` | Package marker. |
| `detector.py` | Functions: `analyze_url()`, `analyze_batch()`. Fully functional, safe heuristic checker — only ever analyzes strings passed to it (never fetches or browses anything). Flags raw IP hosts, excessive subdomain nesting, suspicious keywords (verify, secure, confirm, etc.), known URL-shortening domains, high-abuse TLDs, and simple typosquat/brand-mimicry patterns (e.g. `paypa1`). Returns a `risk_level` (low/medium/high) plus specific reasons. |

### tests/

**`test_simulator.py`** — 17 unit tests covering:
- Hashing round-trips
- Campaign lifecycle and invalid-event handling
- Database read/write/clear
- Anti-phishing detector heuristics
- Flask app routes — including an explicit test that `/phish/event` ignores and never echoes back extra fields like `username`/`password` if a modified client were to send them

## Getting Started

```bash
# Install dependencies
pip install -r requirements.txt

# Seed synthetic sample data (run once)
python data/seed_data.py

# Launch the app
python main.py
```

## Testing

```bash
python -m unittest tests.test_simulator
# or, if pytest is installed:
pytest tests/test_simulator.py
```
